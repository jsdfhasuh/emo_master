# PR #11：停止后启动准入更新与过期图片诊断

实施与记录：**ChatGPT Web**。基线：`5f62eb7e2eb63e097e8e3385de34c96549eabf07`。

本轮依据 Dot 的固定版本可见验收，修正已经确认的正常操作缺口。
本地结果针对该基线加本次改动；推送后的固定提交和双平台 CI 结果以 PR #11 的对应评论为准。

## 1. Dispatch 终态已显示，但启动按钮仍被旧并发限制禁用

### 证据与根因

Dot 在 `5f62eb7` 的同一会话中记录：Stop 后 12:15:43.455 UTC 完成工作流目录查询，
12:15:44.562 首次采样见执行资源退场，12:19:49 UI 仍显示 `E_MAX_CONCURRENT_JOBS`；
明确刷新后按钮恢复。任务状态、两个下拉和原控制卡片已经正确到终态，
失败发生在另一份 `workflows.canStart` 准入快照。

`resolveCommand()` 在回执后只执行一次目录刷新；后续正式 `job_state` 和独立 root 查询
只更新 `runs`，没有在执行资源退场后重新读取工作流准入。
Runtime 的 `startAvailability()` 和 `ownsJobResources()` 使用同一 supervisor 锁内的
`_ownedJobs()` 集合，Dispatch root 还聚合组成员资源，因此不需要增加另一套资源账本。

原可见证据没有保存第一次 workflows 响应体，不能声称读到了该次具体字段。
新增实际 App 回归明确重建了“首次查询仍禁止启动，随后资源退场”的正常顺序：
固定旧源码上失败，修复后通过。

### 修正

- 当前实例/工程内，正式终态且执行资源已退出的 Job 集合变化后，合并触发一次
  workflows 专项读取。重复终态消息不持续轮询，不重新打开 view。
- 只更新准入字段，保留用户 JSON 输入、工作流选择、页面版本、查看和控制对象。
- 共享请求序号和实例/工程/配置校验，防止晚到的旧目录覆盖新的准入结果。
- 仍以 Runtime 返回的 `canStart` 为准；其他任务继续占用容量时保留真实拒绝。
- 查询失败保留错误和已有手动刷新出口；不重发 Start/Stop。

## 2. 停止窗口中的旧图片请求：准确区分退休与读取失败

### 已证实与尚待验证

Dot 的三次资产 404 都靠近 Stop，且三次均有原生确认框等待的记录。
原包没有这些请求的 `scope/resultKey` 与响应 `detail`，不能逐条确定历史返回分支。

本地真实 ASGI 网关反例证明：同一 view 的 `mock-1` 图片最初可读，正常推进至 `mock-6`
后，原有最近四结果边界已淘汰 `mock-1`；再次请求旧 key 返回
`Exact advertised result retired or expired`，当前 `mock-6` 仍可读。
这是有效的生命周期拒绝，不能把旧请求改成返回新一轮图片。

原生 confirm 暂停页面处理、后台继续推进、恢复后先请求积压旧 key 的链路，
已加入真实 Chromium + 正式 Web 网关 + 显式合成 Runtime 的 CI 回归。
本地 Chromium 在进入页面前被环境 IPC 权限拒绝；这不算网页失败，也不算浏览器回归通过。
该链路是否在本轮浏览器实际复现，以对应 CI 的 `asset-retirement-browser/report.json` 为准。

### 修正

- 资产路由保留 HTTP 404 和现有结果保留边界，增加明确原因码：
  `VIEW_NOT_FOUND`、`RESULT_RETIRED`、`SOURCE_UNAVAILABLE`、`FROZEN_RESOURCE_EXPIRED`。
- 失败时在既有 `gateway.request` 记录中保留 view、Runtime、工程、scope、resultKey、source
  和具体失败分支；能取得的 Job/resource 身份一并记录，不写图片字节或任意查询参数。
- 前端把明确的退休、来源不可用和冻结过期显示为 `unavailable`；
  未分类拒绝、真实读取/解码/大小/摘要校验错误仍为 `error`。
- 不补执行、不重读另一份结果、不扩大缓存、不将有效 404 改为 200。

## 3. 原 Windows 双任务用例保留首次错误，即使随后恢复成功

历史 Windows `job_2_image` 失败缺少首错及就绪子条件，原有失败后诊断无法证明
先前发生过但已恢复的暂时读图错误。这个证据缺口不等于历史根因已经确认。

本轮只在原测试中增加有界探针：

- 仅记录该用例登记的两个 Job，在原 `_readImage` 异常返回处保留首错时间、类型、
  gRPC code/details、耗时、完整结果与资源身份。
- 正常成功也写出 `build/two-job-observation.json`；恢复不清除 `firstError`。
- GUI 就绪子条件由主线程另行采集，明确标注非原子、可能已恢复。
- 保留原 0.5 秒 RPC 上限、25 秒条件等待、原断言与执行顺序。
- 首次失败阶段独立保留，清理阶段不会覆盖它；诊断异常不能替换原测试错误。
- CI 上传同一份 JSON，沿正常完整测试顺序执行，不另加重复的 481 项矩阵。

本轮没有给生产客户端增加后台取证机制。

## 4. 实际软件 Runtime 的浏览器验证加强

原 `product_runtime_e2e.py` 继续使用 Chromium → Web HTTP/WS → 独立软件 Runtime。
在原数值、判定和正式状态基础上，增加正式 `blob.overlay` 图像绑定与可解码像素检查。

第一 Job Stop 后不刷新、不重启，等待启动按钮可用；通过页面再启动第二个 Job，

## 6. 验收与归因边界

Dot 下一轮首先固定本次推送 SHA，沿已经授权的本机免密入口操作：

1. 普通任务和 Dispatch 均连续完成启动、出图、停止、再次启动，期间不明确刷新或重启。
2. Dispatch 查看 consumer 时控制仍指向 root；停止后原 root 的资源退出应使正式准入更新。
3. 停止确认框正常停留数秒后确认，记录首次资产拒绝的结构化原因与准确身份，
   检查最新有效结果可继续显示，过期图片不被替换为别轮图片。
4. 保留输入、页面选择及日志查看/导出的原有操作，记录失败与恢复，不只保存恢复后的画面。
5. Windows 原生与真实设备仍按实际执行范围分别记账。

历史 Error 9 仍缺 renderer 所属资源域和终止事件；本轮没有取得新的宿主退出证据。
历史 Windows 首次空图仍需原平台首错资料；新的测试取证与 CI 正常通过不能倒推旧死因。
本轮不合并、不发布 Release、不部署现场，也不声称软件绝对无缺陷。
