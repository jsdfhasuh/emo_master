## 首先补入计划和契约验证的三个边界

### R09：检测顺序与消息顺序独立

每个明确的运行实例/Job/结果作用域及调用位置，在作用域开始时分配单调 resultOrdinal（名字可调整），与 resultKey、用于重放的 streamCursor 分开。跨 Job/运行实例不直接比较 ordinal，不用 UUID 或异步完成时间代替业务顺序。

维护 live 当前指针和有限历史索引两套语义：晚提交的旧结果可以被历史索引接收，但不得覆盖更新结果的 live 指针。新结果为 INCOMPLETE/FAILED 时，旧结果随后成功也不能使 live 回退为旧 OK。锁定详情仍按用户点击时实际看到的 resultKey，不受 live 推进影响。

测试：101/102/103 全部六种提交排列；102 不完整后 101 成功；重复消息、同 ordinal 不同 scope、Job 切换和 generation 更新。服务端 GetDisplaySnapshot 的 latest 与客户端 live 都要保持同一顺序契约，而不只是 UI 拒绝旧图片。

### R10：等待超时不等于任务被终止

P0 必须选择导出任务的执行与回收机制，明确正常、异常、永久阻塞和强杀后线程/进程、IPC、图片缓冲和文件归属。不可把 Future.cancel()、result(timeout) 或 shutdown(wait=False) 当成正在执行任务已被取消的证明。

可验证监督管理的有限导出子进程等可回收方案；这是图像导出执行单元，不是第二个拥有设备的 Runtime。只有协作式任务能有真实退出保证时才可把取消标记作为充分条件。不得通过结束检测 Job 来伪装展示故障隔离；不使用无限增殖 daemon 线程作为回收措施。

测试：实际已开始的导出任务永久阻塞、超时、重复阻塞；结果及时降级，资源槽位和内存有可验证上限，控制仍响应，检测主流程不被展示失败改判。由外层测试监督者设置超时和最终清理，不让故障用例挂死 CI。真实通道损坏/重建按原 R1 规则验证。

### R11：草稿配置隔离与运行状态隔离分开

当前 ProjectGlobalCounters 通过 runtimeDbPath 和 projectId 关联权威计数；新增 debug/release 标签本身不隔离计数。明确新增草稿调试默认使用独立计数和文件输出命名空间，不能静默修改生产计数、重置生产计数或覆盖正式输出。不通过启动另一个争用相同设备/数据库的 Runtime 实现隔离。

P0 一律使用临时项目、临时 SQLite 和输出目录；先验证规则和现有调用点，不在 P0 顺便迁移生产数据库。生产共享状态的例外必须是独立、显式授权策略，不能被“预览”触发。保留旧运行路径语义，设备互斥和现场许可仍然独立检查。

测试：同 projectId 的 release 计数设为 100，debug 增加/清零后 release 仍为 100；debug 文件输出不能覆盖 release 输出；模拟预览不执行算子。此项是新增调试模式的契约，不宣称现有代码已具备隔离。
