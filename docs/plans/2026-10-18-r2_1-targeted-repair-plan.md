## 2. N01：先把运行语义固定下来

### 2.1 根因和完整调用链

固定基线中的实际链路是：

`源周期 → RunGroup.submit → retainCycle → RunGroup.next → retainCycle → _runConsumer → CyclePlanSession.install → While iteration → beginCycle → Runner → dispatchComplete → Join`

`coordinator.py` 的 `beginCycle()` 即使收到 `parentCycleId`，仍使用 `snapshot = self.current`。`retainCycle()` 已保留源快照，但没有保留“这个输入的后续处理不能自行取新版本”的执行约束。消费者结束时又按照原 invocation identity 回报完成。

因此，修复必须改变 **实际安装的配置来源**，不能只改 Join 的标签或在末尾补报一次错误。

### 2.2 选版规则

| 场景 | 快照来源 | 检测周期身份 |
|---|---|---|
| 独立顶层调用开始 | 当时已提交的在线配置 | 创建本次根周期 |
| 自有运行根中的第一层显式 `cycleBoundary=iteration` | 该次迭代准入时已提交的配置 | 创建新的检测周期 |
| 已经进入检测周期后的嵌套显式循环 | 当前检测周期持有的快照 | 继续同一检测周期，用现有调用 / 迭代身份区分内部执行 |
| Dispatch 消费者领取已有输入 | 投递保留的源快照 | 保留源 `cycleId`、配置版本和帧来源 |
| 消费者内部循环、同步子流程、继续 Dispatch | 继续继承源快照 | 不因为多了一层调用而另开业务检测周期 |
| 真正的下一次独立生产周期 | 最新已提交配置 | 新 `cycleId` |

这里沿用已有显式循环标记，不扫描和猜测业务拓扑。没有显式迭代边界的顶层调用仍按整次调用执行；在自有根中明确声明的外层检测迭代可换版，其内部嵌套处理不能再次换版。循环前后属于外层调用的代码，保留现有外层计划恢复语义。

**同一工作流定义可以有两种合法用法：独立启动时可开始新检测；被 Dispatch 作为旧输入消费者调用时必须继承。判断依据是本次调用关系，不是永久给工作流贴“只能当消费者”的标签。**

### 2.3 配置、数据、身份不要混为一谈

固定的是设备默认值、节点覆写、普通参数和绑定定义。PLC 当前读数、计数器、可变全局变量仍按现有运行语义读取，不把所有数据冻结成周期启动时的值。

同一源图在内部循环中继续流转，保留平台帧 ID 和源 `cycleId`。生成派生图时可以有新的帧 ID，但配置版本和所属检测周期不改变，坐标来源按现有契约保留。不要通过修改 FrameRef 的标签，把旧图伪装成新采集。

## 3. N01：具体实现方案

### 3.1 在现有周期记录中增加一个内部属性

建议在现有内存 lease 字典增加 `allowChildRefresh: bool`，只由 Runtime 设置，不写入工程文件、不增加用户选项。

| 周期记录的创建方式 | `allowChildRefresh` | 含义 |
|---|---:|---|
| 自有顶层运行根 | true | 已有显式迭代边界可以开始下一检测 |
| 从自有根创建的检测迭代 | false | 已经选定本轮参数，内层只继承 |
| `retainCycle()` 为投递 / 消费者保留的记录 | false | 接收的是已有检测，不继承重新选版权限 |

名称可随代码风格微调，但不要再平行增加多套“主流程权限、设备权限、周期选版权限”记录。现有 owner、cycleId 和快照关系仍然是唯一依据。

### 3.2 `beginCycle()` 分为创建与借用两种结果

建议在内部返回结构增加 `ownsCycle`，表示本次进入是否真的分配了需要配对退出的周期。它是生命周期标志，不是安全权限令牌。

```text
没有父周期、是自有根入口：
    使用 current，创建根记录，allowChildRefresh=true，ownsCycle=true。

存在父周期，父记录 allowChildRefresh=true：
    使用 current，创建本次检测记录，allowChildRefresh=false，ownsCycle=true。

存在父周期，父记录 allowChildRefresh=false：
    借用已验证父记录的快照、cycleId、planRevision、documentRevision；
    不创建新业务周期，不再放一份 childCycles 记录，ownsCycle=false。
```

复用既有 owner / 父周期存在性校验即可。父周期失效时返回已有的生命周期错误，不能为了“容错”回退到 `current`。

**借用源周期比再造一个子 cycleId 更简单。** 现有 FrameRef 和 Dispatch 要求图片与请求的 cycle / plan 对应；只冻结版本、仍在每个内部循环生成新 cycleId，会把风险转移到原图再分发上。内部层级已有 `workflowRunId`、`nodeRunId`、`iterationPath`，无需新增第二套业务周期 ID。

`knownRevision` 仅用于判断要不要返回配置载荷，不决定哪个版本合法。合法的 R1 投递必须能够在刚处理过 R2 的持久消费者上安装 R1，不能用“只允许版本递增”规则拒绝它。

### 3.3 `retainCycle()` 固定继承，不复制重新选版权限

源记录被保留给 delivery owner，或者由 delivery owner 转给 consumer Job 时：

- 保留同一快照、源 cycleId、执行版本及文档版本。
- 在目标 owner 的记录中设置 `allowChildRefresh=false`。
- 继续使用现有保留 / 退休机制，不复制一个“永不退出”的根任务。

两次保留都必须生效：即使最初直接从自有根投递，后续消费者也不能重新选版。二次、三次分发沿用相同规则，不增加特殊的“第二级消费者”分支。

### 3.4 `CyclePlanSession` 配对处理创建和借用

`scope()` 仍通过现有内部调用取得 Runtime 决定的版本。按实际返回载荷安装参数；同一版本不重复执行无关初始化。

退出时，仅 `ownsCycle=true` 的进入需要对应 `endCycle`。借用作用域退出时不能结束源周期，不能释放源图、其他消费者或尚未完成的外层调用。异常和取消复用已有 finally / owner 退休路径，不新增后台补偿循环。

外层计划保存与恢复继续保留。测试要证明恢复的不只是 `self.revision` 数字，还包括 `document` 和 `runner.compiledProject` 真正对应的值。仅在现有实例缓存确实保存了可热变参数时，修复受影响缓存；不为每个周期复制全部模型或销毁所有算子。

**不要在 worker 中另存一份会与 Runtime lease 分叉的永久 `isConsumer` 真相。** 调用方只负责遵守本次创建 / 借用结果；Runtime 负责快照归属。

### 3.5 排空、停止与身份保持

排空只关闭“新检测准入”，不阻止已受理检测内部的借用作用域。自有根的下一外层迭代仍应在边界停住；消费者的旧投递、嵌套处理和已经入队的必要分支继续结束。判断沿用当前 draining / parked 机制，作必要的创建 / 借用区分，不增加全局屏障。

普通 R2 参数提交时，不等待所有 R1 消费者结束。R1 与 R2 可以并存，但每轮内部的配置来源一致。需要换连接或不兼容资源的原有定向停止 / 排空规则不放宽。

`dispatchComplete` 和 Join 保留现有身份检查；它们不是用来把不正确的结果“重新标成正确版本”的地方。新增测试应检查实际 condition / body 节点值和事件，而非只在完成时多加一次摘要检查。

### 3.6 修改位置

| 文件 / 模块 | 修改职责 |
|---|---|
| `apps/runtime/project_config/coordinator.py` | 内部继承属性；创建 / 借用选择；retain 传递约束；排空入口最小协调 |
| `apps/runtime/project_config/cycle_plan.py` | 处理 `ownsCycle`，正确安装和恢复；借用退出不 end 源周期 |
| `apps/runtime/devices/ipc.py` | 仅透传必要内部字段和既有错误；不增加重复状态机 |
| `apps/runtime/jobs/worker_main.py` | 核对消费者安装、缓存复用及完成身份；只在调用适配确有需要时修改 |
| `apps/runtime/workflow/loop_runner.py` | 保留显式迭代入口和原有取消；借用时仍增加 iterationPath，不强行新建检测身份 |
| `apps/runtime/frame_dispatch/scheduler.py` | 验证 retain 链与原图再分发；无实际需要不修改既有退休 / 回执算法 |

不预设上述每个文件必须改。最终补丁应该由实际闭环决定；不为达到模块数量改无关代码。工程 schema 不因内部 lease 属性升级。内部进程协议如有变化，同一候选里的 Runtime / Worker 一起更新，不热替换正在运行的旧进程。

## 4. N01 的验证方式

### 4.1 先保留真正的失败反例

以独立复审中的旧投递反例为起点：源 R1 的 body 输出 1，旧投递尚未消费时提交 R2 的 99，消费者执行显式 While。修复前应能观察到错误值 99，修复后必须返回 1，且所有相关执行事件为 R1。

## 5. N02：独立修复流程包复制和导入

### 5.1 先修确定的程序错误

在 `apps/designer/state/workflow_package.py` 的 `_populateImportedWorkflow()` 中，把目标工作流变量改为 `targetWorkflow`，Dispatch 枚举变量改为 `dispatchTarget`。本地字典的改变只影响复制中的目标数据，不修改源对象。

这一步单独验证两条路径：工程内复制，以及 schema 1.3 导出→读取→导入另一工程。不能用“不支持 Dispatch 导入”绕过缺陷。

### 5.2 连带验证槽位和端口引用，但不重构调度器

上轮指出的 `targetSlotId` 冲突只是静态风险，先让“原流程和副本一起被同一运行组引用”的测试跑到 Compiler / groupSlots。

若发生冲突，在**一次复制 / 导入的依赖闭包内部**建立局部槽位映射，复用当前调度契约：源闭包中相同且合法共享的槽位仍映射为同一新槽位；新槽位不与目标工程已有槽位冲突。不要全工程字符串替换，不自动改已有运行图的槽位。

变更槽位时必须一起更新 Join 派生输出端口、连接这些端口的边，以及平台已有的类型化端口来源引用。不能只改 Dispatch 的目标字段：基线 `dispatchPorts()` 的 Join 输出就是以 targetSlotId 为键。使用已有引用重绑定机制，缺少的局部映射补齐即可，不新建通用命名空间引擎。

### 5.3 保持原流程包安全和编辑语义

资源字节、大小、哈希、依赖闭包、现场值清空、新设备禁用，以及禁止覆盖已有现场设备的规则全部保留。不得为让导入变绿放宽它们。

失败不污染目标 Store / 撤销栈，只清理本次新建文件；成功仍是一条可撤销草稿命令，撤销保留资源以支持重做。同工程复制继续复用已有设备 / 资源，不因为复制流程就连接或禁用现场设备。

用可被真实 Registry / Compiler 接受的模拟工程验证；涉及留空现场字段和新禁用设备的导入，先验证可编辑保存，再由测试模拟用户填好模拟字段并启用模拟设备后验证可运行。不要把包层 Pydantic 通过当作完整 Runtime 成功。

## 6. N03：独立接通同清单资源修复

### 6.1 正常操作必须可达

保留现有上传入口。LOOKUP 检测到已登记副本缺失 / 损坏时，返回可处理的 `CORRUPT` 结果及对应传输身份，而不是只有异常。界面明确提示“将用本地正确原件修复相同资源”，用户确认后继续，不要求改文件名、改哈希或随便改一个工程参数来制造差异。

服务器不把坏资源当 READY，不降低执行前校验。客户端也不把所有 LOOKUP 错误都当 MISSING：权限 / 实例变化 / 存储异常仍返回原错误，只有明确 CORRUPT 走修复路径。

### 6.2 复用现有分块上传，暂存后切换

修复请求使用新的 transferId，并携带指向待修复记录的显式关系（例如可选 `replacementOf`）。资源的工程身份、规范化清单、大小与哈希必须与待修复对象一致；变更内容应走普通新资源发布，不混为修复。

正确字节写入新的受管暂存文件，复用现有 CHUNK / COMMIT 校验和容量规则。写完并验证后，再在现有 SQLite 权威提交中将新记录设为有效 READY，将被替代记录标记为失效 / SUPERSEDED。旧路径不被原地覆盖。

LOOKUP 与 resolve 共用一个明确的有效记录选择函数。不能靠没有 ORDER BY 的行遍历碰巧选中最后一份，也不能让损坏旧记录和正确新记录长期竞争同一权威身份。兼容已有重复 READY 记录时，按明确规则选择已校验对象；有歧义则报告，不猜测“哪个大概最新”。

这里只增加修复所需的状态或字段，沿用原传输账本，不建立另一个内容分发平台或多后端存储框架。

### 6.3 原子性、pin 与回收的具体边界

文件系统和 SQLite 不声称组成一个跨介质原子事务。顺序固定为：新受管文件写完并按既有要求落盘 → 校验 → SQLite 切换有效记录。提交前失败保留旧在线定义与明确损坏状态；新临时文件由现有受管清理路径回收。提交后响应丢失，查询原修复请求，不再次覆盖或自动生成另一轮修复。

候选准备期间的 pin 和已经持有的执行副本继续有效。修复只替换受管输入的有效映射，不修改正在运行任务的独立物化文件，也不切换在途周期参数。

被替代坏对象在确认无直接准备读者后，交给既有 pin 释放 / 准备结束 / 重启回收边界处理。公开 CANCEL 的在线引用保护不放开；内部退休针对已不再权威、无读者的具体对象，不按相同 manifest 把正确新对象删掉。不要为这一步新建常驻 GC 或无限历史。

### 6.4 修复完字节，还要能够恢复 Runtime 就绪

处于资源恢复失败状态的 Runtime，修复相同清单后可能没有任何工程差异。因此必须提供正常可达的“重试恢复”动作：在空闲、受影响旧使用者已退出时，重新验证和准备**当前已提交配置**，成功后安装软件状态并清除对应资源恢复错误。

优先提取复用现有 `_prepareProjectConfiguration` / publish 的必要部分，并使用现有单写入协调入口。不要重建 Runtime 全部服务，不要求伪造 selectedPaths，不因恢复相同字节重置变量、计数器或推进执行版本。

恢复动作不自动拍照、执行 PLC 节点、重放请求或启动生产；也不调用会重新激活全部设备的通用初始化入口。设备确需连接时仍由既有明确策略或用户动作触发。不是资源问题的未完成设备退休 / UNKNOWN 状态，不能被“清除所有 recoveryError”掩盖。

界面分别报告“资源副本已修复”和“Runtime 已恢复就绪”。若只有字节修复成功、准备仍失败，就如实显示后者，不显示总成功。
