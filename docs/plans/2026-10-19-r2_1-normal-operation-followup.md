## 3. 优先级调整

### 3.1 本轮要改：F02 上传终态与操作出口

正常操作的目标：结果已明确时停止等待；结果未明确时保留原请求，但用户可以继续查询或明确取消。取消不能冒充成功，也不能静默重新上传。

不借此重构整个 RuntimeClient，不新增持久化客户端队列、自动补偿、自动 COMMIT 重试或后台恢复服务。

### 3.2 本轮暂缓：F01 资源对象 pin 组合竞争

保留风险记录：候选尚未被在线工程引用时，准备 pin 的对象与随后 resolve 的对象可能在损坏 / 同清单修复期间分离，再与显式 CANCEL 和配置提交交错。

实施状态为 **DEFERRED_NON_BLOCKING（用户已确认暂缓）**。原审查的证据和严重性分析保留，不篡改历史报告；但该组合不再作为本轮正常操作开发、正常人工走查或隔离台架验收的前置条件。不要求实施 pin 接口重构、跨对象事务交接或新增故障矩阵。

如未来在实际使用中出现，或者发现无需文件损坏 / 并发修复也能通过单一正常操作触发，再按新证据重新评估。仅重复已有故障注入结果，不足以自动重新扩大本轮范围。

本轮不加入该项新的永久运行限制，不要求用户每次上传或启动都确认“不删除文件”。已有损坏校验与明确修复能力继续保留。

### 3.3 不重新打开已修主线

N01 的 `allowChildRefresh` / `ownsCycle`、N02 的槽位与 Join 重绑定不因 F01/F02 再次重写。保留相关测试，不把之前的测试和辅助证据升级为本轮独立实机通过。

## 4. F02 的具体改动

### 4.1 用一个小函数统一传输结果分类

在 `RuntimeClient` 内复用同一套分类，用于上传异常后的 STATUS 和用户稍后的查询。直接处理现有结果，不新增通用状态机框架。

| 原请求查询结果 | 行为 | 是否移除该请求 pending |
|---|---|---|
| READY | 记录本次资源完成；核对成功不是再次 COMMIT | 是 |
| CANCELLED | 记录“原上传已取消 / 当前资源不可用”，不是成功，也不声称 COMMIT 从未发生 | 是 |
| PENDING | 返回“仍待完成”，保留原 transferId，允许明确取消或继续查询 | 否 |
| 无法连接 / 无法确认 | 保留原身份和原错误；不自动 BEGIN、COMMIT 或产生新修复请求 | 否 |
| 实例或工程已切换 | 沿用已有实例 / 工程核对规则；不把旧请求发给新实例，不在此扩展跨重启恢复体系 | 不静默遗忘 |

其他已存在状态按原契约处理并显示明确原因，不擅自归类为 READY 或 MISSING。本轮不为未证实的状态组合继续增加通用恢复功能。

保留现有 `uploaded` 结果字段；按需补充 `cancelled`、`pending`、`errors` 的最小结果信息，让界面区分状态。一个请求已结束就处理它，不因同批另一请求还未返回而丢掉已确认结果；仍未知的请求继续保留。

### 4.2 给仍在等待的上传提供明确取消入口

复用 `TransferProjectResource(..., action="CANCEL")`，使用当前客户端保存的原请求、原工程和原 Runtime 身份，不新增服务器接口。

可以增加一个局部客户端方法，负责取消用户选中的未完成传输。结果收到后按 4.1 分类：只有服务端明确结束，才解除该请求的不确定记录。遇到仍被使用、取消响应丢失或未知结果，显示原原因，不谎报已取消，不擅自删除在线资源。

界面明确区分“取消上传”和“取消待提交配置写入”，避免一个按钮悄悄取消两类任务。采用现有区域中的文字按钮或有明确选择的现有操作入口，不另建管理页面、不增加多层确认。

对已经查询到 CANCELLED 的请求，不再要求用户额外点击取消；直接结束等待并恢复后续操作。

### 4.3 界面状态与按钮同步

调整 `ProjectConfigurationDialog.query()`、`poll()` 和 `_controls()` 的必要分支：

- 显示“完成 X 项，取消 Y 项，仍待核对 Z 项”，只把 READY 计入完成。
- CANCELLED 后移除的是对应请求，不能清空其他仍在处理的请求。
- 没有剩余 pending 时恢复上传；资源恢复按钮还必须满足原本的资源恢复条件，不能无条件打开。
- 仍为 PENDING 时显示原请求身份，并提供取消 / 查询出口；普通查询不重复弹出确认窗口。
- 保持本地草稿、磁盘、撤销栈、在线版本和正在运行的任务不变。
- 若已有请求处于真正未知状态，保持原有不重放语义；这项修复不负责通过“允许再上传”掩盖未知副作用。

## 6. 有限且直接的验证

以下是待执行目标，不是本次已通过结果。可以参数化和复用现有测试，不要求八套测试框架。

| ID | 操作 | 核心断言 |
|---|---|---|
| OP-01 | 正常上传 / 查询 READY | 原行为不变，完成只计一次；无额外修复或配置写入 |
| OP-02 | 原请求暂时未知，之后 STATUS=CANCELLED | 返回明确取消，移除它的 pending；用户能发起后续合法上传；不自动重传 |
| OP-03 | STATUS=PENDING，用户明确取消原上传 | 使用同一 transferId / 实例；确认取消后结束等待；不自动 COMMIT |
| OP-04 | 已有 COMMIT 成功但响应丢失，稍后查回 READY | 不增加 COMMIT / BEGIN 次数，保留原请求查询路径 |
| OP-05 | 查询或取消暂时不可达 | 保留原身份；界面有重查出口；不假报成功或丢弃未知请求 |
| OP-06 | 同批 READY、CANCELLED、PENDING 混合 | 逐项正确记录；终态解除自身 pending，未完成项保留；数量不混淆 |
| OP-07 | 正常 Qt 查询 / 取消按钮与后续上传 | 未完成时可查询或取消，结束后按钮正确恢复；本地草稿 / 磁盘 / undo 不变 |
| OP-08 | 查询或取消被原有身份 / 在线引用保护拒绝 | 显示真实错误，不删除受保护资源；不启动 / 停止生产任务或推进配置版本 |
