## 1. 目标与实施原则

本轮一起完成两个功能：

1. “上一次运行”改为**这个节点上一次实际执行**，同一个视频循环内也能查看。
2. 图像节点完成后即可显示图片，**不用等待整个流程任务结束**，并能查看上一执行对应的图片。

配套处理普通 2K / 4K 图片超出现有解码限制的问题，提供适配预览，不改变后续算子使用的原图。

**按用户最新要求，以正常使用为主，不做过度防御性编程，不考虑极端环境下的完整容错。** 优先修正记录归属、发布时机和文件释放，沿用现有模块；不另建通用框架、资源事务系统或复杂兼容体系。

## 3. 明确界面语义

例如同一任务中，计数节点连续输出 `5、2、3`，面板应显示：

- 本次执行：`count = 3`。
- 上一次执行：`count = 2`。
- 两条记录的输入、数值、图片和执行信息分别来自各自那次调用。

| 操作或状态 | 预期行为 |
|---|---|
| 节点第一次开始执行 | 建立本次记录，显示执行中；没有上一次 |
| 同一次执行完成或失败 | 更新该记录，不轮换历史 |
| 下一次节点开始执行 | 原本次转为上一次，创建新本次，淘汰更早记录 |
| 本次失败 | 本次显示失败，不用上一执行输出冒充；上一次仍可查看 |
| 正常取消 | 当前执行显示取消或中断，不永久停留在执行中；已完成记录保留 |
| 节点被分支跳过 | 默认不算实际执行，不挤掉两次历史；明确显示本轮跳过，旧结果标注原来源 |
| 再次启动整个任务 | 启动本身不轮换；该节点真正再次执行时才轮换 |
| 新任务尚未执行该节点 | 可看已有结果，但显示原任务、原时间，不能冒充新任务结果 |
| 切换工程或 Runtime 重启 | 清理旧上下文，不恢复跨重启历史 |

“上一次”始终指上一实际调用，不是最近一次成功调用。两次执行可以属于同一个 Job，也可以属于连续启动的不同 Job。

界面按钮使用“本次执行 / 上一次执行”，时间使用节点执行记录的时间。选择上一次只影响右侧和大图，不改变画布当前运行状态。

## 4. 最小实现方案

### 4.1 节点两条执行记录

在现有历史模型内调整，不另建历史数据库：

- 按工程副本、运行目标上下文、`workflowId`、`nodeId` 分组，每个节点保留本次和上一次。
- 复用 `jobId + workflowRunId + nodeRunId` 识别执行，同一调用的开始/完成事件更新同一条记录。
- 不同运行目标、工作流和节点不混用历史；循环调用不为每一轮建立永久历史桶。
- 每条记录保留自己的节点名称、端口、版本来源和时间，不用后改的草稿覆盖历史。
- Job 继续负责启动、停止和日志来源，不再决定“保留两次”的单位。不能因第三次启动 Job 就删除仍属于节点最近两次的记录。
- 复用现有摘要归一化与事件去重。保持 `NodeRunInspection` 对实时画布提供最新状态的语义，不让历史选择反向影响运行状态。

### 4.2 节点完成即可读图

继续使用现有 Runner 采集位置、图片文件存储和资产读取接口：

1. 节点输出校验后，使用现有采集位置取得本次图片，不在视频、YOLO 等各个算子里重复增加显示代码。
2. 图片记录绑定本次执行与端口；节点完成后即可查询，不再把整个 Job 终态作为图片可读条件。
3. Runtime 与 Designer 使用相同的执行身份选择本次/上次图片。摘要继续走事件，图片继续走资产接口，不把图片塞进事件日志。
4. 修改现有删除规则，保留两次执行的图片。已发布图片由检查存储统一管理，采集端不在下一帧到来时直接删除。
5. 复用现有读者引用：第三次执行可以淘汰最早历史，但已经开始读取的文件要等读取结束再释放。这是普通循环会遇到的情况，不新增通用资源交接框架。
6. 图片在后台读取/解码，编码或文件复制不放进 GUI 线程和事件分发锁。若需要延后处理，不能保留会被下游改写的数组作为历史图片。
7. 图片采集失败只显示该执行图片不可用，不改变业务执行状态；已失败的节点不能被提前采到的图片标成成功。
8. 保存结果图沿用已注册的工作区副本和现有回执，不从可能已被后续执行覆盖的输出路径取“上一张”。

沿用现有会话清理和额度，不为此次功能新增复杂预算体系、无限队列或后台补偿服务。只保留两次记录，不积累整段视频历史；资源不足时明确说明图片不可用，不禁止正常运行。

### 4.3 查询与界面联动

- 在现有查询请求中补充所需的 `workflow_run_id`、`node_run_id`，客户端按执行和端口取图。
- proto 使用新增字段方式扩展，生成桩通过 `scripts/gen_proto.py` 更新，不手改生成文件。不为此单独建设多版本协议框架。
- 复用 `InspectionImages` 的单工作者、后台解码和迟到结果隔离。相同选择不重复读取，切换节点/端口后旧图不能覆盖新选择。
- 运行中刷新跟随节点结果与图片就绪，不再只依赖 Job 结束。只处理当前选择，不轮询全工程所有节点。
- 数值、输入、执行信息、图片和大图均绑定选中执行。图片尚未就绪时显示等待，不先拿其他执行的图填充。
- 普通连续循环必须能持续看到结果，避免每次新事件都取消读图，导致界面始终空白。
- 关闭查看器不停止任务；一次断连后的恢复沿用既有重连机制，不新增断网补执行或自动重放。
- 版本不支持时明确说明图片能力不可用，不显示错误来源；本轮不要求支持任意新旧版本组合。

### 4.4 大图适配

Runtime 从本次冻结图片生成保持比例的显示预览，默认适配 `1920×1080`，不放大小图。仍超过现有编码读取上限时进一步缩小，使用有限处理，不无限重试。

来源记录原始尺寸，传输尺寸描述真实预览。主面板和大图标明原始/预览尺寸，继续共享一份显示像素。预览不能替代业务原图、保存原图或算子调试输入；本轮不新增全分辨率分块浏览功能。

## 7. 正常路径验证

优先复用现有夹具和受控算子，用不同数值和不同颜色/像素标记确认执行对应关系，不依赖真实设备或大型模型。

| ID | 场景 | 核心断言 |
|---|---|---|
| V01 | 同一个任务连续执行三次，输出 `5、2、3` | 本次为 `3`，上次为 `2`，开始/结束事件不会重复轮换 |
| V02 | 真实 Runtime 循环，末端保持运行 | Job 仍为 RUNNING 时能查看两次对应的数值和图片，不靠等任务结束让测试通过 |
| V03 | 再次启动任务、切换节点/端口/运行目标 | 节点实际执行才轮换，不同上下文不串图；界面和大图一致 |
| V04 | 本次失败、正常取消、分支跳过 | 状态明确，不冒充成功，不卡在执行中；上一次实际执行仍可查看 |
| V05 | 读取上一张时产生下一次执行 | 正在读取的图片不被提前删除；更早历史正常淘汰，不累计所有帧 |
