## 1. 目标与边界

交付三项互相配合的能力：采图快于消费时通过可取消的背压等待持续运行；消费流程每次完成后发布人脸数量、标注图等业务页面结果；在现有“全局变量”窗口增加“运行队列”标签页，让用户不必翻日志就能查看排队、处理和完成情况。

核心决策是 **共用查看窗口，不共用变量存储**。业务变量继续使用现有定义、生命周期和 Runtime 状态库；队列监控直接查询 Dispatch 调度器的权威运行状态，不把图片或队列对象写入全局变量，不根据日志推算队列长度。

三项均为正式实施与验收项，不再把队列满等待和消费者页面发布列为后续备注。调度行为只在显式选择等待模式时扩展，队列监控仍为只读，不把页面查看变成控制任务的入口。

| 纳入本计划 | 不纳入本计划 |
|---|---|
| “业务变量 / 运行队列”双标签页及只读队列查询 | 修改用户真实 RTSP 工程、访问摄像头或播放声音 |

沿用现有工程顶层 schema，不为本次功能新增顶层配置体系。Dispatch 节点参数新增可选的队列满策略与等待超时，缺省保留旧行为，并同步规范、编辑器、校验与保存重读。页面优先复用现有消费者入口 result scope，不虚构异步 Dispatch 为同步调用路径。

顶部使用“运行组”选择器，不复用业务变量页的 Job 选择器。优先定位当前 Job 所属的活动组；没有匹配时，唯一活动组可以直接选中，多个活动组则要求明确选择。显示生产流程名称、运行状态和短 ID，完整身份放入详情。

主表每行对应一个 `targetSlotId`，显示消费流程、等待 / 容量、处理中、累计入队、已完成、失败、状态。同一消费工作流可被不同槽位使用，不能仅按工作流名称合并。

表格下方展开所选槽位的“队列项与图像明细”：

- 显示生产 Job、消费 Job、槽位 ID、实际队列满策略，以及取消数、拒绝数和最近一次失败 / 拒绝的简短原因。
- 当前处理项在前，等待项按实际 FIFO 顺序排列，显示调用 ID、状态、入队时间、开始处理时间和等待位置。
- 图像信息只显示实际存在的 frameId、尺寸、dtype 等元数据。入队时间不是摄像头采集时间，不能混用。
- 队列项不等于图像：一个 invocation 可以有零张、一张或多张图片。主表以消费调用为计数单位，单项展开后再看图片元数据。
- 折叠时不请求逐项明细；展开时只查询选中槽位，按现有容量最多显示 64 个等待项及 1 个处理项。单项图像元数据亦设显示上限，并标注剩余数量，避免返回任意大输入结构。

首版不增加自动缩略图，也不提供队列设值、复位、清空、启动、停止或重放按钮。

### 3.4 状态与错误提示

| 情况 | 显示要求 |
|---|---|
| 活动组存在、队列为空 | 显示真实的等待 0；处理中单独显示，不能把空队列当作全部处理完毕。 |
| 消费进程尚未就绪 | 显示“准备中”，不冒充空闲可消费。 |
| 等待数达到容量 | 显示“队列已满”；实际有生产者在等待容量时再显示“生产等待中”，不能仅凭队列满推断等待。当前仍可能有一项正在处理。 |
| 生产者结束、消费者仍处理 | 显示“生产已结束，消费处理中”，保留有效队列数据。 |
| 正常停止与资源退休中 | 显示“停止中 / 释放中”，跟随真实状态，不把取消计为完成。 |
| 组已释放且终态可确认 | 显示“运行组已结束，队列已释放；未保留结束快照”。数量显示不可用，不填 0。 |
| 无活动组或历史组无法确认 | 分别显示“当前没有活动运行组”或“该运行组已不可用，未保留队列快照”，不猜测成功、失败或取消原因。 |
| 连接中断或查询失败 | 保留最后成功快照并明确标记“数据已过期”和快照时间；没有成功快照则显示不可用。不能继续显示为实时正常。 |
| 旧 Runtime 不支持接口 | 队列页显示“不支持队列监控”，业务变量页仍正常使用；不自动升级、重启或重写工程。 |

首版仅列出活动组，并可保留当前窗口已经观察到的所选组标签用于显示结束状态；不承诺关闭窗口后还能浏览全部历史组。新连接、Runtime 实例变化或项目切换时，不把旧组的消失直接判作正常结束。

错误区采用一条简明原因和可展开的错误码 / 详情，不每秒弹窗或追加重复错误行。重连后下一次成功读取即可恢复，无需用户重启任务。

## 4. 数据来源与统计契约

### 4.1 单一权威来源

等待数取 `len(slot.queue)`，处理中取 `slot.active`，槽位配置和身份来自当前运行组。累计计数在调度器现有状态转移处维护，为每个 Slot 增加少量内存标量，不建立另一份队列或调用状态账本。

| 字段 | 口径 |
|---|---|
| `queued` | 已接纳、尚未开始处理的消费调用数。 |
| `capacity` | 等待队列容量，不包括正在处理的一项。 |
| `processing` | 当前槽位正在处理的调用数，现实现为 0 或 1。 |
| `acceptedTotal` | 成功进入本槽位队列的累计调用数，按目标槽位分别计数。 |
| `completedTotal` | 已接纳调用明确到达 `COMPLETED` 的累计次数。 |
| `failedTotal` | 已接纳调用明确到达 `FAILED` 的累计次数，包含现有 worker 退出终止语义。 |
| `cancelledTotal` | 已接纳调用按现有调度逻辑到达 `CANCELLED` 的累计次数。 |
| `rejectedTotal` | 未进入本槽位队列的拒绝次数，不计入 accepted 或 failed。 |

背压等待尚未接纳，不属于 `queued` 或 `processing`；非终态容量探测不递增 `rejectedTotal`。生产侧等待信息单独显示实际阻塞目标与等待起点，不能把轮询次数当作拒绝次数。等待取消或超时不计入已接纳调用的 `cancelledTotal`，而作为生产侧结果显示。

同一槽位的同一快照应满足：

```text
acceptedTotal = queued + processing + completedTotal + failedTotal + cancelledTotal
```

每次有效状态转移只计一次；重复提交返回已有回执时不重复计数，重复结束通知不重复增加终态数量。计数语义服从现有调度结果，不为满足显示而改变停止、失败或未知副作用处理。

累计值自运行组创建开始，到组释放结束，不是项目历史总量。现有回执清理不得影响累计值，也不能为了监控而保留全部历史 invocation、输入图像或输出图像。

### 4.2 只读查询接口

新增专用只读 RPC，建议命名 `GetDispatchQueueState`，不要把队列字段混进 `GlobalVariablesReply`。

- 请求携带项目 ID、可选运行组 ID、可选明细槽位 ID及是否包含队列项明细。
- 回复包含当前项目的活动组摘要、选中组的可用性、槽位快照、服务端快照时间，以及必要的错误码和简短原因。
- 服务端校验项目与运行组归属，对 `dispatchGroups` 按组 ID 去重；来自其他项目的 ID 不得返回数据。
- 不可用状态与数字 0 必须在协议上可区分，不能依赖 proto 默认数值来代表“尚未查询”。
- DTO 使用显式字段白名单，只返回展示所需元数据，不返回原始 inputs / outputs、共享内存句柄、设备配置、连接凭据或完整工程。
- 只读请求不启动任务、不修改配置、不写全局变量数据库、不调用 `retain` / `release` 改变帧所有权。

先在现有 supervisor 同步边界内取得去重后的组引用，再在对应 `RunGroup.lock` 内生成小型一致快照。遵守现有锁顺序，不新增全局大锁；序列化与网络发送在锁外进行，不在持锁期间读图、编码或访问磁盘。

兼容处理只覆盖本次新增接口的实际需要：旧客户端继续使用原 RPC；新客户端遇到旧 Runtime 的 `UNIMPLEMENTED` 显示明确提示，不创建通用跨版本适配层。

### 4.3 刷新策略

默认沿用 1000 ms 刷新，不新增高频推送、刷新频率设置面板或独立监控服务。

- 当前窗口及对应标签页可见时才发起自动读取；切入队列页立即读取一次。
- 同一页面最多一个读取请求在途，慢请求期间跳过定时触发，不排队积累请求。
- 项目、连接、运行组、槽位选择和窗口生命周期参与结果身份校验，晚到响应不能覆盖新选择。
- 窗口关闭或隐藏时停止自动查询；已发出的请求仍按现有安全销毁方式收尾，不能阻塞 UI 等待网络。
- 变量页与队列页的只读轮询互不叠加；变量写请求的结果交付与现有保护不受影响。
- 自动刷新保持当前选择、展开状态和滚动位置，不每秒重置用户正在查看的内容。

队列监控的预期开销主要是少量整数计数和每秒一次元数据读取，尚无实测性能结论。监控链路验证“不复制图片、不逐帧写库、不积压轮询、不阻塞主线程”；业务页面的图像传输仍走现有有界展示链路，不能把监控的低开销结论外推为图像展示没有成本。本轮不额外设立压力测试或摄像头节拍专项。

## 5. 队列满时的可取消等待

### 5.1 策略与兼容

在 Dispatch 节点 `params` 增加节点级 `queueFullPolicy`，取值为 `error` 或 `wait`。缺省为 `error`，原工程保留 `E_DISPATCH_QUEUE_FULL` 和现有部分目标接纳错误语义；本次双流程验收工程显式选择 `wait`，不依赖队列扩容维持运行。

等待模式增加 `waitTimeoutMs`，缺省为 0，仅允许非负整数。0 表示在目标仍可用的情况下等待到有容量或用户取消；正值为本次逻辑投递的总等待上限，超时给出明确错误与阻塞槽位。计时采用单调时钟，不随一次容量查询重置。编辑器只在等待模式下展示此项；保存、重开、流程包导入导出及编译须保留和校验新参数。

该策略作用于本 Dispatch 的全部目标，避免同一次扇出同时混用等待与报错语义。等待只针对容量暂时不足；消费者退出、运行组停止、输入非法或通信结果不确定，都不能伪装成“继续等容量”。

### 5.2 接纳与等待实现边界

- 生产 worker 对本次输入只采集、翻转和编码一次；保持原 `dispatchSequence`、cycle 和输入身份等待，不每轮重新采图，不生成新逻辑投递。
- 调度器在现有 `RunGroup.lock` 内检查目标有效性以及所有目标的容量；等待模式下任一目标满时，返回明确的非终态等待结果，不先投递给有空位的目标。
- 等待结果不创建已接纳 delivery，不形成终态拒绝回执，不推进本次请求的终态去重高水位；已有成功回执仍按原身份返回，防止响应确认后再次入队。
- 容量判断与实际接纳在同一次受锁保护的操作内完成，不能先查有空位、解锁后再盲目入队。输入或资源错误仍按现有结果处理；如果出现已部分接纳的失败，保留真实回执并明确失败，不自动重放已接纳目标。
- 调度器立即返回等待状态；由生产 worker 在锁外按现有短间隔、可检查取消的方式再次请求接纳。等待期间不占住调度锁、设备服务线程或 Qt 主线程，不妨碍消费者取出、完成和用户停止。
- 只对明确的非终态“等待容量”继续同一次投递；通信失败或副作用未知时沿用原错误与不重放边界，不实现通用重试或后台补偿队列。
- 在现有运行组对象上保存最小的当前生产等待摘要，供监控显示；接纳、取消、超时、生产者退出时清除，不建立独立调用历史账本。

### 5.3 停止、资源与连续运行

用户停止时，生产侧及时退出等待，取消后不得补投递。组内已排队和正在执行的调用继续沿用现有停止及退休语义，不暗中改成“必须消费完才可停止”。消费者退出或组进入停止状态后，等待者应获得明确终态，不永久挂起。

等待中的帧和 cycle 保持原生产者所有权，接纳后按现有 delivery 引用转交；取消、超时或失败按原退出路径释放，不提前回收消费者仍使用的帧，也不因监控或等待重复 retain 图像。

等待时暂停下一轮采图，进度受消费能力约束；缓冲仍限于配置队列、正在处理项和生产者当前待投递项，不增加隐藏无界缓存。这保证的是已采集并接纳工作的处理语义，不承诺保存摄像机产生的每个物理帧，也不把 RTSP 自身缓存和丢帧行为列为本次修复内容。

## 6. 消费者业务页面结果发布

### 6.1 页面归属与查看入口

每个消费 Job 使用其工作流入口对应的 `presentationForWorkflow()` 结果。检测数量、标注图和留档结果属于消费流程的作用域，不能继续挂在生产者 Job 身份下，也不能把 Dispatch 伪装为同步 `subflow` 来绕过校验。

在临时验收工程中，将相关页面的数据源明确绑定到消费者入口和实际检测节点 / 输出，保留所需页面布局与业务含义。同一页的数量和标注图来自同一次消费结果；首版不在一个页面内拼接不同 Job 的异步结果。原工程页面不会未经绑定调整就自动迁移。

现有查看页面入口需能从所选生产 Job 定位所属运行组的消费结果。单消费槽位且只有该消费者有业务页面时，可直接显示其页面并标明来源；多槽位时在现有查看上下文中选择结果流程 / 槽位，不要求用户到任务列表猜测消费 Job ID。同名工作流的不同槽位保持独立。

### 6.2 接通完整发布链路

1. 在同一已保存的工程及页面版本上，为有页面的消费者冻结普通运行 capture 配置，沿用已上传资源的解析映射与现有校验，不重复扫描设备或执行算子。
2. 复用现有 PresentationService 的 `attachNormal()` 为每个实际消费 Job 注册独立配置与资源，在启动该消费者前将正确配置传入 `JobProcessSpec`，替代当前无条件的 `presentation=None`。无页面的消费者继续不启用采集，不能把生产者的配置对象原样共享给多个子 Job。
3. 持久消费者每次 `runner.run()` 对应一次完整的消费工作流调用；在该次调用的现有作用域开始、输出和结束边界采集并提交，不等待持久 Job 退出后才产生页面结果。YOLO 算子缓存和留档冷却继续复用，不为发布页面重复执行检测或保存。
4. 保留已有页面结果身份和 revision / ordinal 检查，并关联 `runGroupId`、`targetSlotId` 与 Dispatch 调用身份。现有 collector 的 `invocationId` 使用 workflowRunId，不能直接覆盖为 Dispatch invocationId；两者应明确区分并建立必要关联。
5. 结果沿现有 collector、结果存储、图片资产、订阅与 Qt renderer 链路展示。正常启动、部分启动失败、停止、任务退休和再次运行均纳入现有资源释放边界，不能让消费页面留下孤立 reader、共享内存或订阅。

### 6.3 显示语义与副作用边界

- 页面显示最新可用的消费结果，并标明来源与结果时间；采图仍在前进时，也不能把旧检测结果当作最新采图帧。
- 同一结果的标量与图像身份一致；图像仍在准备、失败或不可用时如实展示，不使用上一帧图片冒充当前数量对应的图像。
- 新一轮运行、切换组 / 槽位、页面配置变化后，旧会话的晚到结果不得覆盖当前页面；断连与结束状态按现有结果有效性规则明确显示。
- 页面有界采样、丢弃过期显示帧或关闭观察窗口，不等于取消业务消费或丢弃留档任务；不因看页面而反向控制队列，不把显示次数当作检测完成数。
- 复用现有图像按需订阅、预算和资源管理，不为每个消费结果增加永久图片存档；业务留档仍由原留档算子及冷却规则决定。
- 页面采集或展示失败沿用现有普通运行诊断与失败边界，明确区分业务检测 / 留档结果和展示错误，不因此重复执行已有副作用。

## 9. 双流程工程联动与交付边界

队列满等待和消费者页面发布已在第 5、6 节升为正式必做项，必须与队列监控共同完成第 8 节验收，不能只完成“看队列”就宣称本计划交付。

实施阶段使用不含真实凭据的临时 2.7 工程：生产流程 While 采图、翻转后以 wait 模式 Dispatch；消费流程每次只执行一轮检测和留档，由平台消费循环持续取项；页面绑定消费入口的实际输出，监控查询同一运行组。

临时工程的并发额度满足一个生产者及各持久消费者，不在消费工作流里再嵌套无限 While。验收保留图像方向、保存冷却、模型 / 算子缓存等既有业务语义；用可识别的模拟输入与受控慢消费证明路由、背压和结果一致性，不把模拟检测当作真实模型精度验收。

临时工程须做格式校验、保存后重读、编译和 Designer 实际打开验证。用户真实 RTSP 工程的转换、在线写入与摄像头验收仍需按明确授权执行，不能因为平台功能计划获准就自动修改现场文件、凭据或启动设备。
