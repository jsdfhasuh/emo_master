## 3. 验收副本与观察方法

1. 复制 [响应式布局演示.emoproj](../testing/2026-10-30-canvas-responsive/sample/响应式布局演示.emoproj) 到 Dot 的临时验收目录。通过 Designer 的实际打开入口加载副本，再另存为本轮工作副本。不要修改仓库内演示原件。
2. 样例是工程 2.8 / Presentation 1.1，无设备、外部图片、业务查询依赖。页面有根级上下排列、图片与结果并排组、四指标换行组和表格。流程只有两个边界节点；验收三对象分布前，必须通过 GUI 添加至少三个普通、无设备的节点，不能假定样例已包含完整测试流程。
3. 流程连线使用当前算子库中端口类型相容的纯计算节点，在 GUI 中添加、连接和改标题。无需启动检测；记录所用算子名称。没有合适节点或端口时，将对应连线用例记阻塞，不访问硬件补齐。
4. 页面可通过 GUI 新增临时组件或页面，构造不同尺寸 A/B、两层容器、长标题与三控件排列。新建使用当前 Designer 默认格式，不通过手改 JSON 坐标预先摆好最终结果。
5. 每个用例开始时，记录页面/流程、选择对象、参考线/吸附状态、画布缩放、页面预览宽度与窗口实际大小。先保存稳定起点，避免把前一步未保存修改误认为当前动作产生的 dirty。
6. 一次撤销的判断使用 GUI：从已保存起点完成一个操作，再撤销一次，检查布局恢复和未保存标记；重做一次应恢复结果。仅观察撤销按钮可点不足以证明“一次操作一条历史”。
7. 允许在 GUI 保存之后只读比较工程文件，辅助确认组件 ID、顺序、父容器、绑定与布局规则；不通过修改 session、调用排列/拖放/resize 方法或注入内部模型来完成待验收操作。

真实拖动的最小过程是：在可见目标上按下鼠标键，保持按下，经过多个可见位置移动，观察拖动中反馈，再在目标处释放。离散点击、直接写坐标、`QTest`、pytest、内部 `QDrag` 替身或调用 `drop()` 均不算本轮操作系统拖放验证。

### 4.1 宽度与缩放须分别记录

预览宽度决定页面如何重排，画布缩放只改变编辑视野。分别记录这两个数值，不能用缩小画布模拟窄窗口，也不能把较窄页面截图当成缩放热点验收。

优先在可用桌面上覆盖约 1200、800、480 逻辑像素的预览宽度，并做一次连续宽→窄→宽。平台字体、窗口装饰、原生最小宽度与屏幕大小可能限制实际尺寸；若窄值不能到达，记录实际窗口/内容宽度。只验收确实达到的尺寸，不强行改平台尺寸约束或开启另一套 renderer。

拖影热点至少取得 50% 和 150% 各一段拖动中证据；多选从 B 抓取的证据中要同时说明 A/B 尺寸不同、B 是实际按住对象。截图只能证明所截瞬间，不能据单张静态图宣称拖动全程没有卡顿。

### 4.2 表格与数据证据边界

演示工程不含业务数据来源；设计示例只显示 3 行，原生离线模拟也可能是空表。不能用空表截图声称纵向滚动、分页或查询状态保留已通过。

第一轮先用可见原生预览验证列头、列宽与表格内部横向滚动。若 3 行没有产生纵向滚动范围，则将“带行数据纵向滚动/选择保留”单列为未执行及原因；如可通过已有 GUI 配置一个临时本地 SQLite 表格，可补充执行：用标准 SQLite 工具或 Python 标准库仅在临时目录准备约 100 行合成记录，然后在 GUI 中配置读取并滚动、选择、调整宽度。数据文件准备属于夹具准备，操作应用仍须通过 GUI；不读用户数据库，不修改应用模型或启动真实设备。

补充数据路径应单独注明是 SQLite 原生组件，不能冒充普通结果集合表格已覆盖。没有已配置来源的图片、按钮导航、真实查询或结果会话也同样按实际执行范围记账。第一轮不因样例缺乏业务结果而扩大成设备接入或数据链路改造。

## 5. 页面对齐按布局关系验收

页面采用响应式容器，六种菜单命令不能按流程自由坐标方式一概验收。先确认选中项属于哪个父容器及该容器排列方向：

| 父容器排列 | 部分同级选择可执行的对齐 | 需要完整同级组的对齐 | 等距分布 |
| --- | --- | --- | --- |
| 上下排列 `vertical` | 左、水平居中、右；只改所选项的交叉轴规则 | 顶、垂直居中、底；作用于父组主轴规则 | 垂直，至少 3 个且选中完整同级组 |
| 并排/自动换行 `horizontal/wrap` | 顶、垂直居中、底；只改所选项的交叉轴规则 | 左、水平居中、右；作用于父组主轴规则 | 水平，至少 3 个且选中完整同级组；换行后按各行分配 |

所有对齐仍要求至少 2 个对象。“完整同级组”是同一个父容器的全部直接子控件；跨容器选择不能当作完整组。先使用“操作”中的横向/纵向/自动换行编组建立明确范围，再执行对应方向命令。存在未选择兄弟时，主轴操作不可执行及解释原因是正确行为，不应为了让全部菜单始终可点而修改未选项。

为观察对齐，使用“适合内容”宽度、不同自然高度及留有可用空间的实例。控件填满交叉轴或主轴没有剩余空间时，规则可能正确而外观暂不变化；改宽度/尺寸后再观察，并只读核对保存的规则。不要把“强制裁剪内容、制造重叠或跨行保持固定像素间距”当作期望行为。流程中的等距分布保持两端坐标，页面中的等距分布按响应式剩余空间布局，两者分别验收。

## 6. 证据、失败与复测

每轮使用独立目录，例如 `docs/testing/2026-10-30-canvas-responsive/dot-desktop/<run-id>/`；大体积视频可以放在 Dot 可交付的独立目录并在报告链接，不要求为此提交所有媒体。至少保存：

- `environment.md`：OS/架构、Python 路径与版本、PySide2/Qt、显示与缩放、实际 HEAD/实现 SHA、dirty 状态、启动命令、窗口与桌面操作能力。
- `results.md`：逐项结果，真实操作步骤、预期/实际、工作副本、页面/流程、窗口尺寸、预览宽度、画布缩放、证据路径。
- `screenshots/`：菜单状态、流程拖前/中/后、页面宽/中/窄、不同缩放热点、编组层级、resize 预览与结果、非法输入恢复、重开结果。
- `recordings/`：可获取时保存简短拖动/resize 录屏；保留真实速度，不以剪辑删去卡顿、闪烁或错误片段。
- `failures/` 与 `retests/`：原始失败和后续复测分开；保留必要日志、复现工程副本及补丁 SHA/工作区差异。

结果仅使用四态：

| 状态 | 定义 |
| --- | --- |
| 通过 | 在记录的真实 GUI 环境完成该操作且满足预期，有对应证据；注明只覆盖的子项 |
| 失败 | 操作已执行，观察到与预期不符的产品行为；写清触发、后果和证据，不凭推测定根因 |
| 阻塞 | 缺少可用桌面、受支持依赖、OS 拖拽能力或明确前置条件，无法有效执行；写明解除条件 |
| 未执行 | 本轮尚未尝试或未覆盖的子项，例如样例没有可滚动行数据；不能写成通过或省略 |

推荐逐项记录格式：

```text
用例：R03 / 多选 B / 150%
首次结果：失败（或通过、阻塞、未执行）
源码：完整 SHA；相关未提交修改：有/无
环境：OS、显示缩放、窗口实际大小、预览宽度、画布缩放
步骤：从哪个控件哪个位置按下，经过哪里，在哪里释放
预期：...
实际：...
证据：截图/录屏/日志/验收工程路径
影响与最小处理：...
修复记录：补丁 SHA 或 diff 路径；没有修复则写明
复测记录：另一次执行时间、源码、结果、证据；首次失败保持原样
```

发现可稳定复现、影响本轮正常路径的问题，先保存失败证据，再做局部最小修复；不在未留证据时改实现、调夹具或放宽预期。修复后复测原失败步骤及直接受影响的相邻用例，并记录新的基准。源码测试可作为修复辅助，但 GUI 失败必须回到相同原生操作复测才能关闭。无法复现或原因未定位的条目保留原状态和已知事实，不把后来另一场景的通过覆盖它。
