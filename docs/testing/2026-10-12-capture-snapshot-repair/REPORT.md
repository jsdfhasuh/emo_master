# 编码期间的捕获通道占用修复

基线为 `29209392b37bd0b95df511f0c2ca89c9b03f058a`。本轮继续处理捕获额度造成的图像不完整，
交付范围是有界图像副本、父子进程确认协议及对应诊断。保留原分支已有 UI、导航与算子修改。

## 固定 SHA 的失败证据

GitHub Windows 诊断 [38244847162](https://github.com/jsdfhasuh/emo_master/actions/runs/38244847162)
使用精确基线 SHA。它是运行诊断失败，不是编译失败。四组各执行 96 次，源图 AVAILABLE
依次为 85、94、92、96。两组启用观察的 arm 分别在 36/41 和 5/9/17/20 拒绝捕获。
全部六次申请都发生在前一个任务完成回复到达之前；等待尚余约 6.6–61.3ms。
这不能继续细分为编码、写文件或 OS 调度的独立责任。

观察组已有 186 次成功导出都满足完成回复→归还→接管。上一轮修复实际生效，但
“图像尚未编码完成时仍占据唯一共享 lane”仍会拒绝下一张。实际捕获间隔并非严格 200ms，
最短相关间隔约 58.5ms，不能只按标称 5Hz 判断是否可能相撞。

arm 0 的 ordinal 1 缺失观测，同时有一次导出超时；证据不足以确认二者是同一事件，
也不能把它算成第 11 次捕获拒绝。原始公共 JSON 及独立审计均保存在证据包中。
JSON SHA256：`3f96beb3a912b91906e4bc7f824d1f43b1874727f659b7aa79a21366ee93ee8a`。

## 实现与所有权

- `exporter.py::encodeWorker` 在共享原图上取得一份独立副本，大小严格不超过该 lane
  的容量，再发送 `snapshot` 确认。编码与文件写入只使用私有副本。每个串行子进程至多
  保留一份输入；成功或失败后丢弃，下一次分配不保留旧副本。图像不经过 Pipe。
- `ExportPool._run` 验证阶段、taskId、成功状态、精确字节数与原期限，随后归还共享
  lane。它继续等待单独的 `complete` 回执，再接管 PNG。副本确认不代表结果已经可用。
- 两段等待共享提交时开始的 500ms 期限。包含排队、复制、确认、编码和文件写入，
  没有给第二段重新计时。客户端原有 550ms 接收/解码额度未改变。
- 一个后继图可占据原共享 lane；第三个同来源图仍在容量耗尽时明确拒绝。另一 lane
  不可借用。旧任务收尾不删除后继的 pending、不重复归还它的额度。
- 未确认副本时的错误必须证明子进程退出才归还。确认之后的错误仍回收编码进程，但
  不再次归还共享 lane。错误身份、错误字节数、重复确认、超时和回收失败都有回归；
  无法证明回收时仍隔离整个 slab。
- 资产接管/清理仍串行，slot 的 active/busy 继续保护 Job 归属与 staging 文件，
  防止后继覆盖前一张 PNG 或过早重新分配 slab。

每 Job 共享原图仍为 8MiB，双来源各 4MiB，最多两个待处理共享原图描述符；每个编码
进程最多另有一个已复制的任务。输入副本计入原有每编码单元 6×8MiB 的保守预留。
两个 Job 总共享容量 16MiB、导出预留 96MiB、整体预留上限 256MiB 均未扩大。
此账本不是整个 Python/OpenCV 进程 RSS 的硬上限，测得 RSS 另列于 VALIDATION.json。

父进程诊断新增 `parent.snapshot_poll`、`parent.snapshot_recv`。原来的 pipe poll/recv
继续指最终 PNG 回执。成功链路要求两个阶段各出现一次；公共报告保留新增原始行。
历史证据缺少新阶段时不能被当前协议判为完整。证据脚本没有改采样次数、分母或丢图门槛。

## 验证与首次失败保留

实际 spawn 编码器通过事件暂停在 `imencode` 入口，第二张覆盖共享原图后才恢复第一张编码。
基线确定性失败一次，修复后单/双 lane 均能接收第二张，且两张不同 PNG 逐像素一致。
原有慢资产接管测试继续覆盖两张图身份、独立文件、异常回调和资源归还。

首轮相关回归为 122 PASS / 1 FAIL / 1 SKIP / 12 subtests，失败是报表仍按每调用 19 行
计算。更新为 21 行并逐项核对两个新增阶段各 96 行，保留原报告容量和全量行完整性断言。
第一次扩大回归中止于新增超时测试清理：已经终止等待事件的子进程后，测试又调用该
跨进程事件的 set，清理未返回。删除该测试清理中的通知，仍由真实 pool.close 回收；
未改产品超时规则。中止记录和原日志均保留。随后额度/故障测试 38 PASS。

最终扩大回归：821 PASS / 1 SKIP / 26 subtests（378.49s）。范围为 runtime/core/UI
presentation，以及公共报告/hosted guard 测试。Ruff、mypy（411 源文件）、proto drift 均通过。
没有在本机重跑全项目 pytest；完整 CI 另按精确提交记录。测试组有重叠，不相加。

单独 Windows 原生 Qt ABBA 首次运行：四组各 96/96 源图 AVAILABLE，无不可用来源或
缺失源观测，导出 completed=96、timeout=failed=0。每组两个消费者均正式接收/解码/live
应用 88/88。两个观察组各 96 次 snapshot→release→最终回复→callback 顺序成立，
无丢失观察行；四组 owner retirement 均证实。单 Job 实测固定预留 192MiB，上限 256MiB；
共享容量 16MiB、导出预留 96MiB。各进程 RSS 另列，不与预留账本混为同一指标。

整体仍为 INVALID / performance NOT_ASSESSED：arm 1 两个窗口 committed/painted 均
84/88，缺 71、73、82、84；arm 3 两窗口 committed=80/88、painted=78/88，完整缺号列表
见 VALIDATION.json。arm 0/2 两窗口均 88/88。首次结果没有重跑，不把源图与消费完整
写成端到端全通过。

源码身份和完整统计见 `VALIDATION.json`。自动化、脚本化原生 Qt 与可控故障注入不替代
Designer/Runtime 人工操作；本机结果不替代精确交付 SHA 的 Actions 结果。

## 未关闭范围

有界缓冲吸收一次短时重叠，不能保证持续编码/接管吞吐不足或任意负载都不缺图。
必须独立统计源图 AVAILABLE、两个消费者接收/解码、live 应用、Qt 提交/绘制。
源图完整不能代替后三者。首次观测与开始订阅的竞争、历史 NG→INCOMPLETE 的未确认
路径、Windows SQLite 的历史失败及 P0 相对性能结论不由本轮自动关闭。

只正常提交推送原分支；不合并、发布、部署或连接生产设备。
