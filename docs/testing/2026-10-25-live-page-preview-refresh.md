# 实时页面预览刷新与窗口拖动

日期：2026-10-25。源码 HEAD：`9265547dbe61bc57542d3cf0ea143fcf455600fb`。
基于该提交上的现有未提交工作区，仅修改共享页面渲染器及本轮测试、记录。
没有提交、推送、打包、部署，也没有连接相机、PLC 或修改现场工程。

## 触发条件与确认的问题

用户确认：只有实时图片不断变化时，拖动预览窗口标题栏和调整窗口大小才感觉卡顿。

本轮确认了会增加界面线程开销的三处重复刷新，但没有将其认定为现场所有卡顿的唯一根因：

- 每次 `RuntimePages.submit()` 关闭再开启整个窗口的 updates，会把未变化的区域也标记为重绘。
- `ImageView.setImage()` 即使收到同一张缓存图片、同一结果身份和同一提示，也请求重绘。
- 判定指示器即使样式不变，也在每次结果提交时重新设置 stylesheet。

修复沿用 Qt 的排队合并重绘：同一次 GUI 线程提交先更新控件和结果身份，返回事件循环后再绘制。
没有插入 `processEvents()`，没有把图片与数值拆成不同更新周期。
同一图片的结果 key 改变时仍请求绘制，以保留真实的绘制身份和计时记录。
不降低现有 16 ms 检查频率、图片分辨率或业务执行速度，不暂停检测，也没有新增线程或图片缓存。

## 前后对照

环境：Python 3.10.21、PySide2 5.15.2.1，Qt offscreen。
仅使用合成页面和双路 1920×1080 BGR 图片，不运行 Runtime、RPC、算法或设备。

首轮定位使用 cProfile：60 次更新时，原实现静态区域绘制 120 次；临时跳过整窗 updates 开关后为 0 次。
该轮平均耗时为 6.240 ms 和 4.040 ms，但不是最终修复的稳定收益承诺。

最终使用 HEAD 中原始 `submit` / `setImage` 方法与当前方法进行进程内 ABBA 对照，不改写工作区文件。
每轮预热 20 帧，统计 120 帧，包含 hub 提交、图片转换及排队绘制处理，不包含测试结果构造。
图片、计数和结果编号持续更新；静态文本与 OK 样式保持不变。
