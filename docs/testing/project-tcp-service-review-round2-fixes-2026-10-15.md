## 三项修正

### 监听异常与重新启动

`communication/manager.py` 的异常路径统一进入 `_failService`：设置 FAILED，停止接收循环，关闭监听与已有客户端，撤销会话租约并唤醒等待。异常线程不获取控制锁或等待自身退出，避免与显式 STOP 的 join 互锁。

再次显式 START 时先清理 FAILED 状态的残留资源、等待旧线程退出，再创建监听。若 socket 清理失败，返回 `E_TCP_RELEASE_FAILED`，保留资源归属，不增加服务代次或创建新监听器。线程启动失败也使用同一异常清理路径。

验证包括：accept 抛错后旧端口拒绝连接；直接 START 后独立客户端能接收新工作流结果；意外通信线程异常关闭已有客户端并撤销旧会话；注入 close 失败时保留监听所有权，解除故障后才能重新启动。

### 发送回执与连接代次隔离

管理器记录每个通道最新的连接代次，新连接接入时清空“最近发送”。发送收尾只有仍属于同一项目加载、服务代次和最新连接代次，才允许更新当前摘要。

同项目的旧发送完成仍可留下历史记录，但记录顶层使用原服务代次，不混入新服务身份；旧项目的延迟完成不写入新项目历史。修正不改变发送字节、失败语义或无自动重试规则。

验证分别跨越服务重启、单纯断开重连、同 ID 不同文件替换三个边界。独立客户端收到的字节保持正确；旧 finally 放行后，新连接摘要仍属于新发送，旧记录的服务和连接代次正确，项目替换后的历史没有旧项目完成事件。

### 设置保存的编辑基线与保护

设置页打开时冻结本地配置和对应 Runtime 状态；后续轮询只刷新监控，不自动给旧草稿换上最新修订号。保存先以原修订号调用 `PREPARE_SAVE`，取得 Runtime 保存保护后才在 GUI 线程沿用原项目保存入口落盘，最后携凭据 SYNC。

普通保存与原有禁用保存共用一个有界保护，不增加多事务队列。原 `PREPARE_DISABLE / ABORT_DISABLE` 保持兼容；普通保存新增 PREPARE_SAVE 和状态字段 savePending，禁用保存继续保留停止服务的前提。管理协议仍为 1.1；不支持新动作的旧 Runtime 会拒绝准备阶段，不能继续写入新通信配置。

- 并发修改在文件写入前被拒绝；错误包含冲突提示，设置页保持打开、可编辑，草稿不丢失。
- 文件保存期间拒绝另一客户端的配置覆盖、启动及项目替换。普通配置保存不停止已有监听和连接。
- 保存失败撤销保护；保存前关闭窗口或本地配置再次变化，也撤销保护且不写文件。
- 准备回执丢失时撤销未落盘操作；提交回执丢失且配置一致时只确认，不再次提交。
- 提交后已有另一份新配置，或者项目身份已经改变时，恢复操作报告冲突，不用最新修订号覆盖，也不自动重新加载旧项目。
- 尚未落盘的新项目先保存保留原通信配置的项目文件；新草稿取得保护后才写入。已存在但未加载的项目先从磁盘原配置建立 Runtime 上下文并校验基线，不先落盘新草稿。

保护不自动过期。发起窗口丢失且保护仍存在时，沿用显式重启 Runtime、重新加载磁盘项目的保守恢复方式；不自动启动或重放报文。“同步已保存配置”在没有待确认事务时仍表示用户明确选择本地已保存配置，不是自动合并远端配置。
