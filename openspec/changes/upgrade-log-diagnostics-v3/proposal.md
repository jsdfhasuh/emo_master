# 共享日志工作台 V3

## Why

本计划基于 2026-11-28 的远端 `main` 提交 `ea5aefa9cf62f0d7ee3ac0fb6fa4a14661dc663b`。Designer 和 Operator 共用任务日志工作台。R4 的 Operator 本机日志使用 `QTableView` 和 `LogTableModel`，已有组合筛选、等级着色、脱敏复制和阅读位置保持。

在此前的 `d3421670` 审查中，通过实际 Supervisor 和临时 SQLite，把事件保留量设为 4。写入一条错误后送入 7 次心跳，内存和数据库最后都只剩 4 条心跳，历史查询从 1 条错误降为 0 条。SQLite 初始回执中的 `UNKNOWN` 还会被当作开始消息，任务级事件也会出现在“未完整关联事件”下。点击节点分支还会关闭详情，现场需要再从事件子行中找出对应记录。

## What Changes

### M1 正确性与失败定位

- 周期心跳在 Supervisor 更新判活状态后结束处理。新产生的周期心跳不占业务序号、保留配额，也不再出现在逐 Job 的事件订阅中。同步更新正式心跳持久化与订阅说明。旧数据库沿用已有读取语义。
- 区分 SQLite 的开始消息和最终回执，修正子工作流分类，让本机 JSONL 纳入子工作流及普通 SQLite 起止事件，并保留后台最终回执。
- 合法的任务级事件按任务归类。暂停阅读时固定内部工作流、轮次和节点的估算耗时，运行中的 Job 继续按自身状态计时。点节点打开同次执行的记录，失败提示先给出已有的轮次、流程、节点、代码和短原因，再跳到对应原始事件。

### M2 可独立交付的增强

| 改进 | 实施范围 |
| --- | --- |
| 历史名称 | 在普通任务和派发子任务创建时保存工程和实际工作流名称。已有受理事件和关键生命周期事件写入本次执行中可取得的名称。旧记录缺值时，使用能确认同一工程、同一修订的名称或真实 ID。 |
| Markdown 导出 | 从 Designer 和 Operator 的完整 Job 导出入口写出可读时间线。范围为固定上界内仍可查询的事件。Operator 的当前筛选快照继续使用其独立入口。 |
| 本机与 Web | Operator 在 R4 表格中接入共享默认文案和摘要，支持按显示文字或原文搜索。Web 支持本地毫秒时间范围，列表和详情均显示易读的框架默认文案。 |
| 桌面查阅 | 节点行展示已有摘要，折叠分支提示告警或错误数量。复用共享中文文案，支持按日志代码、流程名、节点名和已加载内容搜索。历史列表从第 1 轮显示，目录显示最近活动并可查完整工程 ID。在 Job 抽屉直接看该次设备事件的报文与回执，再按需下钻。 |

## 后续可选项

两轮对比单独留作备选。出现具体现场案例时，再确定工程师要找的是状态或输出变化，还是耗时变化。可以按状态、结果筛选差异，耗时差另列。本版需求、实现清单和发布验收均以 M1、M2 为范围。

## Impact

- Runtime 的主要改动在心跳处理、事件消息和 JSONL 筛选。名称增强涉及现有 jobs 表迁移、任务读模型和必要的协议尾随字段。正常重启会把旧活动任务收尾，本期沿用现有单条和批量裁剪。
- 桌面复用 `ui/runtime_logs/`、共享文案和已有导出器。Web 的展示改动使用现有日志查询与导出接口。
- 基础契约沿用主线正式规格，两份增量规格只描述变化。验证按本次新增或改变的行为补断言，现有原生 Qt、Runtime 和 Web 用例可直接复用。具体安排见[实施与验收清单](tasks.md)。
